# Staging runtime forensics — 2026-07-18

## Verdict

`ROLLBACK_STAGING` was correct. No traffic split or edge cache was observed.

## Cloudflare evidence

- Failed deployment `ffb376ae-bad3-44b9-a8b6-ad5a444b8906` was 100% traffic,
  created at `2026-07-18T02:55:29Z`.
- It had `APP_VERSION=staging-2026-07-18T02:55:18Z-fd0a6c9b`, staging D1/R2
  bindings, and script ETag `b0cb0b40dce06a0e5808048beccb2fd781c7066661289baab63d44893c8ab1bd`.
- Rollback deployment `605a92ec-1d2f-40ae-8d2f-cbe1a7619aa2` restored
  `7f8bee25-8d7b-446d-84dd-184b636b0910` at 100% with the recorded message
  `Rollback staging: maintenance gate registered after route mounts`.
- The restored runtime returns the legacy 403 on all four canonical
  maintenance URLs. It reports the older `a4bffd61` application stamp and
  `X-AirTrust-Version: UDI`, demonstrating that the old header is a colo, not
  a Worker version.

## Root cause

`APP_VERSION` was a deploy-time binding, not bundle provenance. The candidate
version was deployed with a code path in which the maintenance gate was not
effective before maintenance router handlers. Those handlers emitted the
legacy localhost 403. The source at `fd0a6c9b` and a clean dry-run bundle both
contain `isMaintenancePath` and `localMaintenanceNotFound` before auth, so the
stamp alone could not prove that this source bundle answered the request.

The tracked `worker-airtrust/.tmp-worker-bundle/` also contains the legacy
message and must not be used as an input to a release. The current deploy
workflow must prove bundle identity through Cloudflare version metadata.

## Required release evidence

The next staging deployment must be 100%, return one Cloudflare Worker Version
ID on `/api/version`, `/api/health`, and all maintenance 404 responses, and
pass repeated nonce/no-cache probes before production is considered.

## Evidence classification (added 2026-07-18, PR #360 completion)

To avoid re-treating a textual claim as cryptographic proof, every statement
in this document and in the deployed provenance headers falls into exactly
one of these three buckets:

### Proven (verifiable independently of this pipeline's own claims)

- The gate/mount ordering in `worker-airtrust/src/index.ts` is correct:
  `isMaintenancePath`/`localMaintenanceNotFound` is registered on
  `app.use('/api/*', ...)` before any `app.route(...)` call. This is proven by
  `src/__tests__/routes/index-temporary-endpoints.test.ts`, which mocks
  `auth`/`tenant` to always succeed and still observes a pure 404 on every
  maintenance path in `ENVIRONMENT=staging`.
- `worker-airtrust/.tmp-worker-bundle/index.js` (removed from tracking by
  this PR) contained the legacy `"Rota disponível apenas em localhost."`
  string — confirmed by direct binary inspection, hash recorded in
  `AIRTRUST_LOCAL_ARCHIVE_20260718/incident-evidence/`.
- No deploy script or CI workflow references `.tmp-worker-bundle` as a build
  input (confirmed by exhaustive grep across `scripts/` and
  `.github/workflows/`), so the stale tracked artifact is not proven to be
  the cause of the 2026-07-18 403s.
- `X-AirTrust-Worker-Version` (Cloudflare's own `CF_VERSION_METADATA.id`) is
  a Cloudflare-attested runtime identity for the exact Worker Version that
  answered a given request — this is Cloudflare's own binding, not a claim
  made by this repository's pipeline.

### Pipeline-attested (the deploy pipeline's own claim about what it built and sent — not a Cloudflare-side cryptographic guarantee)

- `X-AirTrust-Source-SHA` / `X-AirTrust-Source-Tree`: the git commit/tree that
  `scripts/deploy-staging-worker-safe.sh` had checked out when it built the
  bundle.
- `X-AirTrust-Worker-Bundle-SHA256`: the SHA-256 of the `.js` module the
  script's own `wrangler deploy --dry-run --outdir <mktemp dir>` step
  produced, immediately before the real `wrangler deploy` step reused the
  same patched config. Because esbuild bundling happens twice (once to get a
  hash to publish, once for the real deploy), the script and CI workflow
  both re-bundle a second time with `--outdir` on the *real* (non-dry-run)
  deploy and compare that hash to the published one, aborting on mismatch.
  This is detection, not prevention: by the time the comparison runs, the
  vars (including the published hash) are already live on Cloudflare, so a
  caught mismatch means "treat this deploy as suspect and redeploy/roll
  back", not "the wrong value never shipped". A hard guarantee would require
  bundling once, hashing, then deploying a second time with the verified
  hash — not done here to avoid doubling the network deploy on every
  release.
- `X-AirTrust-Release-Manifest-SHA256`: the SHA-256 of a manifest document
  (repository, sourceSha, sourceTree, workerBundleSha256, wranglerConfigSha256,
  toolchain versions, buildTimeUtc, dirty) generated by the same script run.
- These three values prove internal consistency of one pipeline run (the
  hash the script computed is the hash it published), and — combined with
  repeated matching responses across independent probes over several minutes
  — constitute strong operational evidence. They do **not** prove that
  Cloudflare's edge served bytes that hash to `workerBundleSha256`; no
  Cloudflare API was found (or is available with this repository's tokens)
  that returns the deployed module's bytes for independent re-hashing. See
  "Residual gap" below.

### Residual gap (not closed by this PR)

- There is still no cryptographic proof, independent of this repository's own
  deploy tooling, that the bytes Cloudflare executes for
  `X-AirTrust-Worker-Version: <id>` hash to `X-AirTrust-Worker-Bundle-SHA256`.
  Closing this fully would require a Cloudflare API that returns downloadable
  version content for independent re-hashing; this was not available to us
  with the credentials used in this session. Until then, treat the bundle
  hash as pipeline-attested, not Cloudflare-attested.
- Researched: the Cloudflare Workers Versions "get version detail" API
  (`GET /accounts/{account_id}/workers/scripts/{script_name}/versions/{version_id}`)
  does **not** return the deployed module's source bytes — only metadata,
  bindings, and a `script.etag` described as "hashed script content". The
  2026-07-18 rollback evidence above already recorded such an ETag
  (`b0cb0b40...`). This ETag is a secondary, Cloudflare-computed content hash
  that a future incident could cross-reference against a locally-recomputed
  hash *if* Cloudflare ever documents its exact canonicalization — but as of
  this PR we do not know that algorithm, so we do not claim ETag equality as
  proof. This is future work, not something this PR resolves.
- Do not claim "hash proves content" in any future incident report — only
  "hash matches what the pipeline that ran this deploy computed and
  published, and this was independently observed to be stable across N
  repeated probes."

### Probe results (proven, not pipeline-attested)

10 rounds over 5m26s (`2026-07-18T18:31:05Z`–`18:36:31Z`), nonce +
`Cache-Control: no-cache` + `Pragma: no-cache` on every request, 57
probes/round (3 identity + 6 maintenance routes × 9 variants) = 570 total.

- **540/540 maintenance-route probes returned exactly `404` / `"Not Found"`**
  across every tested variant: no secret, invalid `X-AirTrust-Maintenance`,
  invalid `X-Maintenance-Secret`, valid POST body, invalid JSON body,
  trailing slash, double slash, percent-encoded `/maintenance/` segment.
  Zero anomalies.
- **570/570 responses carried identical runtime identity** — one
  `x-airtrust-worker-version`, one `x-airtrust-source-sha`, one
  `x-airtrust-source-tree`, one `x-airtrust-worker-bundle-sha256`, one
  `x-airtrust-release-manifest-sha256` value across the entire run. 100% of
  traffic was on the expected version; no concurrent version was observed.
  570/570 `CF-Ray` values were unique (no cached responses).

This promotes the gate/mount ordering fix from "proven by local test" to
**proven against a real, currently-live staging deployment** — the strongest
evidence this incident produces without a Cloudflare-side content API (see
residual gap above, unchanged).
