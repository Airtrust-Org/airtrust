# Protocolo de Correções — AirTrust

Este protocolo é subordinado a `CLAUDE.md`, branch protection, workflows oficiais, contratos de release e governança de dados/schema vigentes.

## 1. Confirmar base e escopo

- Atualizar a referência da `main` e registrar o SHA de base.
- Preservar qualquer trabalho desconhecido.
- Delimitar o caso real e os arquivos diretamente envolvidos.

## 2. Reproduzir ou caracterizar a falha

- Preferir teste automatizado reproduzível.
- Quando depender de runtime, registrar request, resposta, log ou evidência equivalente.

## 3. Determinar causa suficiente

- Investigar apenas até explicar o caso real.
- Problemas laterais não entram automaticamente na mesma correção.

## 4. Corrigir por delta mínimo

- Preservar contratos HTTP, tenant isolation, RBAC, autenticação e dados.
- Não sobrescrever arquivos atuais com versões históricas inteiras.
- Não usar `git add -A` quando houver alterações desconhecidas.

## 5. Validar proporcionalmente

Ordem padrão:

`teste da falha → teste focado → suíte afetada → lint/typecheck/build aplicáveis → CI oficial`

Não aumentar baseline, reduzir cobertura ou desativar testes para obter verde.

## 6. Integrar pelo fluxo oficial

- Commit somente do delta da frente.
- PR para `main`.
- Respeitar todos os gates definidos em `CLAUDE.md` e branch protection.
- Nunca fazer push direto para `main` nem bypass de gate.

## 7. Staging

Deploy em staging não é consequência automática de uma correção. Quando necessário, usar somente o workflow oficial, o SHA exato e as autorizações/precondições exigidas. Migrations precisam de allowlist, preflight, backup e pós-condições.

## 8. Produção

Produção **nunca é automática**.

Só executar quando houver autorização explícita e atual para o SHA exato, pelos mecanismos oficiais vigentes. Uma autorização consumida por release anterior não vale para SHA novo. Não executar migrations, seeds, restores ou writes remotos por comandos improvisados.

## 9. Encerramento

Declarar separadamente:

- causa confirmada;
- correção aplicada;
- testes e gates executados;
- SHA/PR/merge;
- staging, se realmente publicado e validado;
- produção, apenas se explicitamente autorizada e efetivamente validada;
- risco residual ou blocker real, se houver.

`commit ≠ merge ≠ CI verde ≠ staging ≠ produção`
